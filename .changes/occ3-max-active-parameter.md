Changed: the OCC-3 active-capture admission cap is operator-selectable between 1 and 2 instead of hard-pinned to 1. `RuntimeProfile` now validates `max_active in (1, 2)`; `latent_worker.load_runtime_profile` reads `OCC3_MAX_ACTIVE` after the byte-attested pinned file loads, so the pinned `native_profile.json` (and its PROFILE_SHA256) never moves. Exactly "1" or "2" is accepted; any other value fails closed with a profile error rather than silently changing admission semantics; unset keeps the pinned value.

Changed: the effective value is attested to clients through `binding_digest` (the RuntimeProfile includes `max_active`), and a swap that changes it also changes the container incarnation, so clients re-activate against the new profile through the existing authority path - no client change needed.

Why: with `max_active=1`, parallel senders serialize inside the client's 90 s capture-capacity wait (the second waits ~40 s for the first's arm-to-publish window). `max_active=2` lets both native captures run concurrently. Memory math: calibration floor 88,560,784 B + 78,696,448 B reserved per active capture = 245,953,680 B of the 268,435,456 B `max_live_bytes` budget; the budget gate still fails safe for a third reservation (retryable 503, proven-non-use). Flipping back to 1 needs only a swap without `OCC3_MAX_ACTIVE` - no code change.
