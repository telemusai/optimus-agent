- Added a per-session sender FIFO queue for experimental OCC-3 native handoffs: a completed handoff no longer dead-ends the session - the next `occ3_handoff` call for a new receiver retires the finished slot and queues the handoff; ANY genuinely new request (different receiver, or a repeat while the head is busy) queues behind the current work with its position reported, while the armed head's own two-step arm/publish completion is preserved. Each entry keeps a stable queue id across retries plus an append-only per-attempt message-id history.
- Restart resolution is split by proof: an `armed` entry (no publication exists) is a proven pre-publication failure and fresh-arms within the remaining retry budget; a `published`/`admitted` entry (a publication may have been consumed) resolves to an explicit `uncertain` state - visible, never auto-recaptured, auto-fallen-back or TTL-expired, resolved only through receipt reconciliation or EXPLICIT manual resolution (`sender_queue_resolve_uncertain`: manual re-emit returns the entry to `fallback_pending` with a fresh dispatch token after the human accepts the duplication risk; manual cancel abandons it as terminal `failed` with reason `manual_cancel`; no automatic duplicate ever occurs). A consumed report without a receipt digest also resolves to `uncertain`, never `completed`. LIMITATION (receiver owner confirmed): the receiver-side consumption query does not exist - the receiver drains are exactly-once latched (already-drained entries never repeat), `audit()` has no digests and no auth, and the durable receipts journal is not keyed for sender reconciliation - so uncertain entries remain manual-resolution-only and a resolution query API is deferred to the daemon receipt store owner. Manual resolution is a host-side API only in this change (no user-facing command yet): no automatic caller exists, `reemit=true` is the caller's explicit duplication-risk confirmation, and exposing a user command is deferred to the /occ surface owner.
- Queued state persists as a bounded, content-free `occ3-sender-queue.json` artifact (schema `optimus.occ3-sender-queue.v1`); entry ceiling configurable via `OCC3_SENDER_QUEUE_MAX_ENTRIES` (validated, default 8, clamped 1..=64) and TTL via `OCC3_SENDER_QUEUE_TTL_SECONDS` (default 1800s, clamped 60..86400) with live enforcement (turn/agent-end sweep plus a bounded application-scheduler timer with weak targets - no agent polling); expiry emits a sender-visible terminal `expired` notice without restart, and entries that expired while the session was down are journaled as the same terminal `expired` notices at load (restart expiry is never a silent drop - the notices ride the ordinary durable notice drain, so the sender and the parent-side roster learn of the loss on resume). A refused enqueue (ceiling reached, or the artifact blocked) journals one content-free queue-level `refused` notice - whitelisted `queue_full`/`queue_blocked` values in the details' `refused` key, empty queue id so the record never projects as a queued entry - so a refusal is visible in the durable notice stream and on the parent-side surface, not only as an in-turn tool error. Every queue transition now records its notices into a durable outbox carried by the queue artifact itself (one lock, one atomic temp-file+rename persist of entries AND outbox; a blocked artifact is never overwritten), each with a stable `occ3n_` notice id; a record is removed only after BOTH deliveries acknowledge - the sender-transcript custom-message record (durable append+flush) and the parent notification. Restart replays unacknowledged records with the same stable id, so a crash at any boundary (after the queue save, after the sender flush, after the parent accept) loses nothing and consumers dedup by noticeId; the outbox is capped (64) and hitting the cap flips a persisted overflow flag surfaced in the queue snapshot (`noticeOverflow`) - a visible fail state, never a silent drop. Parent delivery goes through the trusted controller seam (`notify_parent_queue_notice`, default refuses so old hosts keep records pending rather than ack-and-drop): the daemon implementation verifies the caller's identity (the controller's current session must BE the named child), resolves the target exclusively from the child's RECORDED catalog parent (never a caller-supplied name), durably appends an `occ3_child_queue_notice` record to the parent's transcript (rollback on flush failure, full-history noticeId dedup - no window), and queues the same record as a follow-up prompt so an active parent learns the final state without waiting for its next turn. An unknown-schema or corrupt artifact is NEVER silently emptied - the file is preserved byte-for-byte, the queue opens blocked and surfaces a `failed` notice.
- Receiver backpressure no longer burns the capture: consumption and terminal failure events drain through the receiver-side restamp listener (exactly-once `poll_consumed`/`poll_terminal_failures`) and route by SENDER session id through a process-local weak registry to the sending session's queue - never the receiver's own. Admission refusals demote an entry to `fallback_pending` with a fresh dispatch token; queued entries never touch `failed_attempts`.
- Fallback acknowledgment is bound to the host-SCHEDULED fallback re-emission turn: the re-emission prompt is emitted as a dedicated `occ3_fallback_prompt` custom message carrying the (already-public) queue id, and the turn marker is armed ONLY when that MessageEnd consumes a one-shot host-issued prompt record (`issue_fallback_prompt`/`note_fallback_prompt_message`: a spoofed, stale or replayed marker, or one for a since-closed entry, arms nothing). ONLY the ordinary `agent_message.send` made during that dedicated turn - for the entry's own identity, its persisted receiver selector OR the authenticated receiver session id captured at arm time from the authorization - can carry the entry's private dispatch token and close it (terminal `fallback` with that send's actual message id and honest transport status). An unrelated ordinary message to the same receiver in ANY other turn obtains no token and acknowledges nothing. The token itself lives only in host memory and the persisted queue artifact - never in a notice, the transcript, or the UI. Duplicate acknowledgments are idempotent; distinct entries correlate separately.
- Sender-transcript `occ3_queue_notice` records (custom type distinct from `agent_message`) project queue state to the roster's communicationQueue surface without pulsing the activity indicators; after every state change one snapshot-form notice carries the full current queue so a bounded transcript scan always finds an authoritative base. Uncertain notices state their manual-resolution semantics explicitly.

### Round 7: tool-path queue integration (busy-head deadlock + outbox regression)
- `occ3_handoff` on an EMPTY sender queue now creates its stable head entry BEFORE arming: the initial request enqueues its own entry, then arms and transitions that entry to `Armed` with the authorized message id. Every later receiver sees a busy head and queues behind it (position 2, 3, ...); the permit is taken only for the fresh arm. Pre-fix the arm left the queue empty while holding the process capture permit, so the next tool call blocked forever on the single-permit pool (default `OCC3_CAPTURE_CONCURRENCY=1`).
- A same-receiver COMPLETING call no longer reacquires the process capture permit: the active capture (captured lease, or the armed budget for this exact receiver) already holds it. The publish path still validates the exact tool binding; nothing is replayed silently. This un-deadlocks the two-step arm/publish flow at default concurrency.
- The outbox overflow regression (`outbox_record_ack_and_overflow_bound`) now raises the queue entry ceiling to its documented limit for the test queue and probes the 65th RECORD with a hand-built notice, so the refusing surface is the OUTBOX CAP itself - not the default 8-entry ceiling that panicked the previous version of the test at `:1569`.
- Bounded real-tool regressions added: `initial_request_creates_the_head_entry_before_the_arm`, `same_receiver_completion_reuses_the_active_permit` (both completing stages refuse promptly: double-arm, then uncaptured-lease binding validation - never a permit park), and `busy_head_new_receiver_queues_at_position_two` (wrapped in a 10s `tokio::time::timeout`, asserting the head entry exists after the first call). `queued_head_owns_the_next_arm` realigned to the F4 semantics its sibling test already asserts: a different-receiver call on a pending head QUEUES BEHIND (position 2) and never arms.

- Receiver retry fix (expired-delivery resubmission): a receiver inference request that newly supplies an OCC-3 delivery marker whose inbox record already expired now REFUSES loudly (`HandleExpired` -> turn error, no provider request) instead of silently skipping the dead record and falling back to an ordinary text turn. Provenance is explicit, not heuristic: `Occ3InferenceInbox::claim` takes the additionally-supplied `newly_supplied_ids` (extracted by the receiver resolver from the inference request's fresh-input messages), and ONLY a resubmission of a dead delivery refuses - the same record present purely as retained history (both retained copies) never parks the queue and a later unrelated turn proceeds. The rule lives in the claim's terminal-skip loop, so it also catches a delivery that expired silently on an earlier turn (already claimed, never re-enters discovery). FIFO, replay and Consumed/Failed semantics are unchanged; a fresh LIVE delivery alongside expired history still claims and binds normally.
- Internal provenance API (not serialized): `InferenceStateRequest` carries `newly_supplied_messages` - the agent-loop-supplied fresh input of the current attempt (prompt/steering/follow-up lanes only; tool continuations see an empty set). It is a plain Rust field with no wire representation and no migration. Receiver-side regressions: `receiver_resolver_expired_resubmission_vs_retained_history` (real resolver, same session: silent expiry, loud resubmission, history-only skip, live-Y bind with expired X history) and the retained proof's expired-handle test extended with the repeated-refusal and unrelated-turn-recovery legs. NOTE: the retained/agent-loop legs additionally require the pi-agent-core fresh-input population (separate change) to pass.
