- Fixed an OCC-3 private consume corrupting its KV row when its prefill takes a second extend. The private path stashed the committed prefix as an int32 copy of the `req_to_token` row, and the DSA Triton prefix writer in `alloc_for_extend` reads `prefix_indices` through int64 pointers. The row was scrambled, so the model saw the wrong context and the release freed some pages twice and others never. The stash is now an independent int64 copy (`.to(dtype=torch.int64, copy=True)`), as in the stock chunk and radix caches. Single-extend consumes were not affected. The torch fallback writer hides the bug. An already-corrupted KV pool still needs a flush or restart.
- Added a pre-writer guard (`Scheduler._occ3_decline_bad_private_prefix`, `occ3_private_prefix_fault`). Before a private chunked consume's next extend, a nonempty prefix must be 1-D, contiguous, int64, on the row device and no longer than the committed KV. Otherwise the consume aborts with `occ3_private_prefix_invalid` (HTTP 503) through the existing `_occ3_abort_one` path before the writer runs. Metadata only; no GPU sync.
- Added a pre-free row guard (`occ3_private_row_fault`) for private releases. If the row is not page-exact, in range and unique, its pages are leaked and quarantined instead of freed. The decision (`occ3_private_release_fault`) is agreed across TP ranks with a MAX vote over the TP CPU group before any rank frees, so every rank quarantines or every rank frees. The WARNING names the local fault or `peer`. The quarantined tokens are counted by the scheduler and added to the idle memory identity, so the strict idle check does not stop the server. The server keeps running with less free KV until `flush_cache` (which resets the count) or a restart. An ERROR is logged once when quarantined KV exceeds 5% of capacity. The opt-in busy memory check (`SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY`) does not yet count quarantined tokens.
