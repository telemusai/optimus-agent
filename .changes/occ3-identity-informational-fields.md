- Fixed OCC-3 activation declining with connector_unavailable against the deployed DGX runtime: the sglang connector rejected the server identity because two informational provenance fields arrived honestly empty. The extension contract (occ3_sglang/identity.py) degrades an unknown checkpoint provenance (a local model path carries no hub revision) and a chat template kept outside tokenizer_config.json to empty strings, and the client parser and the complete-identity gate refused every empty field, so no live activation could ever parse the real server identity.
- parse_identity (crates/pi-coding-agent/src/core/occ3_connectors/sglang.rs) and complete_identity (crates/pi-coding-agent/src/core/occ/occ3/inference.rs) now treat exactly checkpoint_revision and chat_template_fingerprint as informational: an honest empty value is accepted, while an absent field, an oversized value, control characters and the placeholder tokens (unknown, unverified, none) are still rejected. Every hard identity field (model_id, architecture, weight and tokenizer fingerprints, quantisation, tensor_geometry, kv_layout, latent_method, runtime) still requires a non-empty attested value, so a degraded server cannot smuggle an unverifiable claim as a value and the permit fingerprint still covers the degraded fields (two servers that degrade the same way compare equal).
- Verified red-first: identity_informational_fields_may_degrade_to_empty, complete_identity_accepts_honestly_degraded_informational_fields and activation_accepts_a_server_that_honestly_degrades_informational_fields fail on unpatched main and pass after the change; the strictness guards (hard-field and placeholder rejection) stay green, the full occ3 lib suite passes (91 passed, 2 ignored) and occ3_bridge_offline passes (16/16).
- Known separate gap, unchanged by this fix: the deployed GET /occ3/v1/identity route serves runtime-derived field values (directory-scan weight fingerprint, launch-arg kv_layout, engine label runtime) whose canonical-JSON digest is sha256:58bc47c3..., while the runtime-identity route attests the profile-pinned fingerprint sha256:efef608a... bound to the declared identity. After this fix a conformant-but-degraded server activates end to end (fixture-proven), and the live DGX server now declines at the binding check with model_identity_mismatch instead of connector_unavailable; aligning the deployed identity route with the pinned fingerprint requires the server-side declared-identity change and rides the next planned server redeploy.
