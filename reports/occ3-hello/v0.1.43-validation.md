# Optimus Agent v0.1.43 OCC3 validation

Date: 2026-11-03. **Live native transport and the OCC3 flash passed; exact
marker fidelity did not.** Validation used isolated local Optimus profiles and the
user-authorized, configured DGX MTP (OCC-3) endpoint. No SSH route or provider
credential was changed. Credentials and raw native state are excluded here.

## Changes exercised

- `/occ` exposes enable and disable choices for the experimental OCC3 preference.
- Configuration eligibility requires the explicit OCC3 provider entry. Actual
  native use also requires verified model/runtime identity and family permits.
- Explicit chat preferences gate native actions dynamically and are inherited by
  subagents. Disabling OCC3 leaves ordinary inference available.
- Normal sessions use a two-call native handoff: authorized capture arming, then
  one captured response bound to the same receiver and handoff tool call.
- The system prompt explains scoped hive mind collaboration, exact model
  selection, configured endpoints, native receipts, and ordinary-message fallback.

## Live findings

The original five-second activation deadline was too short for the healthy
gateway. A measured control sequence took 15.984 seconds, including identity at
5.721 seconds and the first enrollment at 5.775 seconds. The new bounds are
15 seconds per control request and 45 seconds for activation. Normal root and
child sessions subsequently activated the verified native connector.

The ordinary `dgx-glm53/glm-5.3` entry displayed “OCC-3 unavailable for this
model”; selecting that action produced the configured-model requirement warning.
The separate `dgx-glm53-occ3/glm-5.3` entry displayed both OCC3 actions.

An initial normal-session attempt armed capture, then received HTTP 409 before
completion. The source capture budget had accounted for retained rows but not
the full tensor-parallel staging allocation. A 128-row v2 GLM capture requires
78,696,448 bytes across eight ranks, exceeding the initial 4 MiB bound. The
corrected budget is bounded by both verified server capacity and 128 MiB. A
fresh direct source probe then returned HTTP 200. The failed attempt did not
produce an OCC3 pulse and was not replayed.

The rebuilt normal agent then completed source capture and admitted the native
handoff between two explicitly selected OCC3 siblings. The source response
contained a private one-word marker and exactly one native handoff tool call;
the receiver's initial context did not contain the marker. The receiver's
guarded inference returned HTTP 409 after roughly 35 seconds. Its diagnostic
was `occ3_inference_uncertain`, cause `http_non_success`. No completed-use
receipt or active OCC3 terminal rendering was observed. This is **not an
end-to-end pass**. The uncertain handoff was not replayed.

A fresh sibling pair then completed native capture, publication, admission and
receiver consumption using the same tested binary and configured model. Its
receiver task included the continuous-embedding framing from the native proof
harness. The receiver first answered `UNKNOWN`; only the sender subsequently
received the private marker `TEAL`. No ordinary message carried the marker to
the receiver. After native use the receiver reported `TEal`: case-insensitive
recovery passed, but exact byte-for-byte recovery failed. This one case is not
a general semantic-accuracy result, nor proof that framing caused the earlier
failure to disappear.

The completed delivery was `agentmsg_44f8cf4e-523e-478c-8dba-30c3ab6eb6e1`.
The receiver's daemon activity classified it as `latent`. The live terminal
recorded `\x1b[1;38;5;39m● OCC3\x1b[22;39m`, followed by the idle `○ OCC3`
rendering. This verifies the real TUI pulse after completed native consumption,
not a synthetic activity event or a queued-send indicator. The 1,400 ms pulse
duration is additionally covered by the indicator tests.

The user's existing running session was also inspected as a reference. Its
agents used `agent_message.send` with manually assembled `OCC/3` text and
invented handles with zero state bytes. There were zero native `occ3_handoff`
calls in that session family; the runtime classified its deliveries as text,
OCC1, or symbolic OCC2. Successful delivery of those strings does not validate
native OCC3. The updated prompt explicitly prohibits that construction.

## Scope of evidence

OCC3 remains experimental. A completed native-use receipt proves native
consumption, not reliable semantic recovery of every source fact. The harness
prompt requires verification of critical transferred facts. In particular, a
short-marker smoke test must not be interpreted as a general accuracy benchmark.

This change affects the Optimus Rust agent harness and terminal UI. The separate
vr-ai-chat 3D and Web product surfaces are not modified.
