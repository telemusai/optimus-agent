## 1. The sequence (one window, one process, no restarts)

All five arms run in ONE serving process in one window, as consecutive turns — that is the whole
point of the control-file mechanism (plan 2.4: "one process serves all three arms in three
consecutive turns"; environment selection would force three restarts and is forbidden). Each
attached arm interleaves its own capture -> publish -> attach cycle, so capture turns and receiver
turns alternate. The order is fixed by plan 4.3 and may not be rotated after arm 1 has run (1.4).
One attempt per arm; a repeated arm is a NEW declared window with a new id that re-runs all five
arms in the same order (4.3).

| seq | turn_id (placeholder `<WIN>` = window id) | arm | role | kind | control file at `/tmp/occ3_p3_arm` |
|---|---|---|---|---|---|
| 1 | `p3-<WIN>-t0001` | N-none | plain receiver | chat, no occ3 keys | ABSENT (operator removes it) |
| 2 | `p3-<WIN>-t0002` | F-text | plain receiver, private sentence between the markers | chat, no occ3 keys | ABSENT |
| 3 | `p3-<WIN>-t0003` | T-exact | source capture | chat + `occ3_capture` | `texact\n` |
| 4 | `p3-<WIN>-t0004` | T-exact | receiver attach | chat + `occ3` + `occ3_receipt_mode` | `texact\n` |
| 5 | `p3-<WIN>-t0005` | T-norm | source capture | chat + `occ3_capture` | `tnorm\n` |
| 6 | `p3-<WIN>-t0006` | T-norm | receiver attach | chat + `occ3` + `occ3_receipt_mode` | `tnorm\n` |
| 7 | `p3-<WIN>-t0007` | N-shape | source capture | chat + `occ3_capture` | `nshape\n` |
| 8 | `p3-<WIN>-t0008` | N-shape | receiver attach | chat + `occ3` + `occ3_receipt_mode` | `nshape\n` (removed after the turn) |

Why the plain arms run first (plan 4.3): `N-none` proves the receiver question is well-formed
before any capture is spent; `F-text` is the answerability reference — if it fails, the two
captures that follow are not spent.

## 2. Turn-id grammar and ranges

* Grammar: `p3-<WIN>-t<NNNN>`, `NNNN` = 4-digit zero-padded sequence allocated strictly in
  execution order. Example with a real-shaped window id:
  `p3-icalib-20261107T041500Z-t0003`.
* Constraint: every wire id must match `[A-Za-z0-9._:/-]{1,256}`
  (`attachment_contract.py:31` `identifier()`; the corpus uses the same class,
  `calibration_corpus.py` `_IDENTIFIER`). Lowercase letters, digits, hyphens only — safe.
* Per-arm contiguous ranges (execution order = id order):

| arm | roles covered | range |
|---|---|---|
| N-none | plain receiver | `t0001` .. `t0001` |
| F-text | plain receiver | `t0002` .. `t0002` |
| T-exact | capture + attach | `t0003` .. `t0004` |
| T-norm | capture + attach | `t0005` .. `t0006` |
| N-shape | capture + attach | `t0007` .. `t0008` |

* Derived wire ids per turn (all in the same reserved namespace, filled by the driver):
  `capture_id = <turn_id>` (capture turns; this is the id that becomes a corpus `turn_id` if a
  capture were ever collected), `p3-<WIN>-req-t<NNNN>` (request ids), `p3-<WIN>-msg-t<NNNN>`
  (message ids), `p3-<WIN>-pub-t<NNNN>` (publication ids, keyed by the capture turn),
  `p3-<WIN>-nonce-t<NNNN>` (turn nonces). The `tool_call_id` for each publish is the id of the
  single `occ3_handoff` call emitted in that arm's source turn (parsed from the SSE stream; it is
  not in the v1 source receipt).
* Sessions: one source session `p3-<WIN>-src` (shared by all three captures — it is the corpus
  `family_id` if any P3 row were ever collected, `latent_worker.py:389`), one receiver session
  `p3-<WIN>-rcv`, `access_domain` `p3-<WIN>` (source and receiver must share it,
  `latent_registry.py:133`).
* Plain arms carry no wire ids at all (no occ3 keys in the body); `t0001`/`t0002` are driver-side
  labels recorded in `turns.jsonl`.

## 3. Determinism and matching

* Source decode is `temperature: 0`, `seed: 1234`, `max_tokens: 4096`, `reasoning_effort: "max"`,
  `stream: true`; the three source captures must carry the SAME `accepted_sequence_digest`
  (plan 2.5) or the phase stops as a framing-equality failure. Never averaged away.
* Consume is single-use: each attached arm needs its own capture (t0003/5/7) and its own publish
  (plan 2.5, step 5).
* The v1 span policy means P3 captures cannot enter the calibration corpus
  (`latent_worker.py:367` requires `prepared["span_selection"]`, built only under v2); the
  fit-exclusion list is the mandatory second line of defence.

## 4. What the driver does per turn

1. Print the operator step for the arm (the driver NEVER writes the control file; plan 2.4/4.1).
2. Wait for operator confirmation.
3. Read the control path back read-only through the declared host command
   (`dgx_ssh.py run` -> `sha256sum`, `stat -c %s`, `stat -c %Y` on that one path, nothing else);
   record `sha256`, `st_size`, `st_mtime_ns` BEFORE the turn; token arms must read back the exact
   staged bytes, plain arms must read back "no file".
4. Submit the turn, consume the SSE stream, parse receipts/terminal event.
5. Read the control path back again AFTER the turn; record both readings.
6. Append one record to `turns.jsonl` (arm, turn_id, wire ids, request sha256, status,
   finish_reason, answer class + sha, receipt summary, control readings, timings).
7. Emit the fit-exclusion file from the recorded turn ids at window close.

## 5. Fit exclusion (summary; full format in FIT-EXCLUSION-FORMAT.md)

Exclude from every P5 partition and M-budget selection: any corpus row whose `turn_id` or
`family_id` is in the P3 namespace (`p3-` prefix for this campaign), enumerated per window by the
ranges above. Excluded rows are NOT removed from the corpus (stage_build.py `p5_exclusion` note).
